# Topic 6.2 — Microservices Auth Architecture: Pattern B — Dedicated Auth/Identity Service, Comparison, and General Patterns

> Scope: continues directly from Topic 6.1. We build out the alternative — a separate, dedicated Auth service — in the same depth, then compare both patterns honestly against your actual constraints (3–5 services, solo platform engineer), land on a concrete recommendation, and close with the remaining general architecture concepts: API Gateway vs. service mesh, Zero Trust for internal traffic, and identity propagation across multi-hop calls.

## 1. The shape of Pattern B

Instead of a module inside BE, authentication becomes its own deployable — a service whose *entire job* is identity: login, token issuance, refresh, RBAC data ownership, and publishing the public key(s) everyone else verifies against.

```
                    ┌──────────────────────────┐
 Mobile App ───────►│      Auth Service          │
 Admin Panel ───────►│  /auth/login               │
                    │  /auth/refresh              │
                    │  /.well-known/jwks.json     │
                    │  HOLDS the signing key      │
                    │  owns users/roles/perms DB  │
                    └──────────────────────────┘
                              │ (public key only, published via JWKS)
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                        ▼
    BE Server            Notification Svc          Rewards Svc
   (verify-only)          (verify-only)             (verify-only)
   business logic
```

The key structural change from Pattern A: **BE is no longer special with respect to authentication.** BE, Notification, and Rewards are now peers from the Auth Service's point of view — all three verify tokens the exact same way (fetch JWKS, check signature locally), and none of them holds the signing key or the users table.

## 2. Walking the flows

### 2.1 Login — now a direct call to Auth Service

```
Mobile App ──POST /auth/login {email, pw}──► Auth Service
                                                │ verify password against users table
                                                │ sign access_token (RS256, private key
                                                │   lives ONLY here)
                                                │ create + store refresh_token
Mobile App ◄── {access_token, refresh_token} ──┘
```

Note this can be reached either directly (Mobile App talks to Auth Service's own public endpoint) or proxied through BE/the load balancer for a single external hostname — that's a routing detail, not an authentication-architecture one. Either way, the code that checks the password and mints the token now lives in its own process, entirely separate from BE's listings/orders code.

### 2.2 BE (and everyone else) verifying a token — no extra runtime dependency

This is the detail that matters most for evaluating Pattern B honestly: **verification does not become slower or add a runtime dependency on Auth Service being up.** Exactly like Pattern A's JWKS approach (Topic 6.1 §3.2), BE fetches and caches Auth Service's public key once, then verifies every request's token **locally**, with zero per-request network calls to Auth Service:

```
BE (on startup, and periodically refreshed):
  GET https://auth-service/.well-known/jwks.json ──► Auth Service
  ◄── { "keys": [...] }

Every subsequent request BE handles:
  verify signature LOCALLY against cached key — Auth Service is NOT
  in the critical path of a single request BE serves.
```

This is worth being explicit about, because it's the most common mistaken assumption about splitting auth out: **Auth Service being down does not mean every other service goes down.** It means *new logins and token refreshes* fail until it's back — already-issued, unexpired access tokens keep verifying fine everywhere, because verification never depended on Auth Service being reachable in the first place. This is a direct consequence of the stateless-JWT property from Topic 2 §3.1, and it's the reason a dedicated Auth Service is a much smaller availability risk than it might initially sound like.

### 2.3 M2M calls — unchanged again, plus one new pair

BE→Notification and BE→Rewards stay exactly as designed in Topic 5. The only addition: BE (and anyone else who needs to) now also authenticates to Auth Service's JWKS endpoint — but that endpoint is deliberately public/read-only (public keys are, by definition, safe to expose — Topic 2 §4.4), so this isn't really an M2M *authentication* problem at all, just an HTTP call to a public config-like endpoint.

## 3. Honest evaluation of Pattern B

### 3.1 What's genuinely good about it

- **The signing key's blast radius shrinks to the smallest possible codebase.** Auth Service can be a genuinely small, focused deployable — login, refresh, RBAC data, JWKS. A vulnerability in an unrelated part of your system (a listings feature bug, a dependency issue in the Rewards service) can no longer reach the signing key, because it's simply not present in those processes at all.
- **Auth-critical code gets its own deploy cadence, review bar, and monitoring.** You can reasonably decide "changes to Auth Service get a stricter review than changes to the listings feature" — a distinction that's awkward to enforce when both live in the same deployable.
- **Genuinely reusable the moment you need it.** Any future service, product surface, or partner integration authenticates against one well-known place, without needing to route through or couple to BE.
- **Matches the "principals aren't all the same shape" lesson from Topic 1 as a deployment boundary, not just a data-modeling one.** Identity becomes a first-class concern with its own home, rather than a responsibility BE happens to also carry.

### 3.2 What it costs you

- **One more deployable to build, deploy, and operate** — a real, non-trivial cost for a solo platform engineer. New Cloud Run service, new CI/CD pipeline, new logging/monitoring setup, new IAM configuration (Topic 5's service-account-per-service pattern now applies to one more service).
- **A new dependency for the login/refresh path specifically** (though, per §2.2, *not* for ongoing request verification). If Auth Service has a bad deploy or an outage, new logins and refreshes stop working system-wide until it recovers — a real, if narrow, availability consideration.
- **Slightly more moving parts for a system this size.** At 3–5 services, the "reusability" benefit (§3.1) is real but not urgent — you don't currently have a second product surface waiting to consume a standalone Auth Service.

## 4. Direct comparison

| | Pattern A — Embedded in BE | Pattern B — Dedicated Auth Service |
|---|---|---|
| New infrastructure | None | One new Cloud Run service |
| Signing key blast radius | Scoped to all of BE's code | Scoped to Auth Service's small codebase only |
| Per-request verification cost | Local, no extra hop (JWKS cached) | Identical — local, no extra hop (JWKS cached) |
| Login/refresh availability | Tied to BE's overall availability | Its own availability, independent of BE |
| Reusability for future products | Requires coupling to BE, or duplication | Reuse "for free" — one identity source for anything |
| Operational overhead | None additional | One more deployable to build/monitor/secure |
| Best fit | Small, stable service count; solo/small team; auth isn't yet a dedicated concern | Growing service count; multiple product surfaces; auth warrants its own security perimeter |

## 5. Recommendation for `mo-marketplace`, given 3–5 services and no near-term growth expected

**Pattern A, deliberately structured for future extraction (Topic 6.1 §5).** The concrete reasoning: Pattern B's biggest advantages — blast-radius isolation and reusability across multiple product surfaces — are real properties, but they answer problems you've told me you don't expect to have soon (you're staying at 3–5 services, solo-operated). Pattern B's cost — one more deployable for one person to build, secure, and operate — is a real, immediate tax with no corresponding immediate benefit at your current scale.

The reasonable middle ground, and the one worth stating explicitly in your proposal: adopt every mechanism this note assumes regardless of pattern (RS256 signing, a JWKS endpoint, a clean `auth/` module boundary inside BE) so that **the moment Pattern B's benefits start to outweigh its costs — a second product surface, a partner API, a growing team where "who touches the signing key" starts to matter organizationally — extraction is a deployment change, not a redesign.** This is a genuinely good, defensible position for a technical proposal: "we're choosing the lower-overhead option today, and we've deliberately kept the door open to the other one without paying for it now."

## 6. The remaining general concepts

### 6.1 API Gateway vs. service mesh — where do these fit in?

Two more architectural patterns worth knowing by name, distinct from the Pattern A/B question above (which is about *where auth is issued*) — these are about *where authorization/routing policy is enforced* across a system.

**API Gateway pattern:** a dedicated piece of infrastructure (a managed product like GCP API Gateway/Apigee, Kong, or similar) sits in front of all your services, handling authentication verification, rate limiting, and routing in one place, before requests ever reach your application code.

```
Client ──► API Gateway ──► BE / Notification / Rewards
           (verifies token, rate-limits,
            routes by path — ONE place)
```

**Service mesh / sidecar pattern:** instead of one central gateway, every service gets a lightweight proxy ("sidecar") running alongside it, and all inter-service traffic flows through these proxies, which handle mTLS, retries, and policy enforcement transparently (Istio, Linkerd are the common names here).

```
┌─────────┐sidecar┌─────────┐sidecar┌─────────┐
│   BE     │◄─────►│Notif Svc │◄─────►│Rewards  │
└─────────┘       └─────────┘       └─────────┘
     Every arrow secured/observed by the mesh, not by app code
```

**Where you actually sit:** your GCP Load Balancer + BE already functions as a de facto API Gateway for external traffic (it's the single entry point for Mobile/Admin), and Topic 5's Cloud Run IAM invoker bindings already give you the core security property a service mesh would otherwise provide (verified identity on every internal call) — **without taking on a mesh's operational complexity.** A formal API Gateway product or a service mesh becomes worth adopting once you have enough services that manually configuring IAM bindings and JWKS caching per-service starts to feel repetitive, or once you need mesh-specific features (automatic mTLS everywhere, fine-grained traffic shaping). At 3–5 services, what you're already building in Topics 4–5 **is** the lightweight version of both patterns — worth naming explicitly in your proposal as "we evaluated API Gateway/mesh and chose to achieve the same properties natively via GCP IAM, appropriate to our scale," rather than looking like an oversight.

### 6.2 Zero Trust for internal traffic — pulling Topics 1–5 together under one name

Topic 1 §6.2 introduced Zero Trust as a principle; here's the complete picture of what you'll actually have, once Topics 1–5 (and this note) are implemented:

```
┌──────────────────────────────────────────────────────────────┐
│  ZERO TRUST, APPLIED — every arrow independently verified       │
│                                                                    │
│  Mobile → BE          : user JWT, verified every request (T2)     │
│  BE → Notification     : Cloud Run identity token (T5), NOT the    │
│                          user's JWT — separate, scoped credential  │
│  BE → Rewards          : same as above                             │
│  Notification/Rewards  : platform-level IAM check BEFORE app code   │
│    ← Mobile (blocked)    even runs (T5) — no implicit network trust │
│  BE → CloudAMQP        : per-role credentials, least privilege (T5) │
└──────────────────────────────────────────────────────────────┘
```

Nothing here is "no trust ever" — Zero Trust doesn't mean paranoia about every packet, it means **no arrow is trusted by virtue of network location or a prior hop alone; every arrow carries its own independently-verifiable proof.** You've now built exactly that, one topic at a time, without needing to name it explicitly until now. This is a genuinely strong, coherent story for your proposal: "we didn't buy a Zero Trust product — we applied the principle at every boundary using tools we already have."

### 6.3 Identity propagation across multi-hop chains

Right now your chains are short (BE → one downstream service). If a future chain grows longer — BE → Service X → Service Y — two *different* kinds of "propagation" need to be kept conceptually separate, a distinction worth having ready even though you don't need to build it yet:

**Authentication/authorization context** (who's allowed to do what) — per Topic 5 §7.4, this should **not** simply forward blindly hop after hop. Each hop re-establishes its own service identity (Service X proves it's Service X to Service Y, using its own Cloud Run identity, not by forwarding whatever BE sent it), while the `onBehalfOfUserId`-style business context can ride along as plain data, because each hop is independently authenticated.

**Correlation/tracing context** (which request is this, for debugging/observability) — a *separate* concern, carried via a request ID that has nothing to do with authorization at all. Since you don't have this set up yet, the standard, low-effort starting point is a simple generated ID attached at the first hop and passed through unchanged:

```http
X-Request-Id: 8f14e45f-ceea-467e-bd2b-e0b6f7a9c3f4
```

```
Mobile → BE                    (BE generates X-Request-Id if not present)
BE → Notification               (BE forwards the SAME X-Request-Id)
BE → CloudAMQP → Notification   (X-Request-Id travels as a message header/property)
```

Every service logs this ID alongside its own logs (this pairs naturally with the `nestjs-pino` structured logging you've already worked through) — so a single user-facing request that touches BE, then Notification, then a queued job, can be traced end-to-end by grepping one ID across three separate log streams. This is a genuinely low-cost addition worth doing regardless of the auth-architecture decision, and it's the natural on-ramp to the fuller Cloud Trace integration you explored earlier, if you want request-level tracing with timing later. Worth flagging as a small, separate action item in your proposal — it's not an auth mechanism, but it makes everything in Topics 1–5 dramatically easier to debug when something does go wrong in production.

## 7. Summary

| Decision point | Recommendation for `mo-marketplace` |
|---|---|
| Where auth lives | Pattern A (embedded in BE), structured for clean future extraction |
| Gateway/mesh | Neither, for now — GCP IAM + BE-as-entry-point already gives you the core properties |
| Zero Trust | Already achieved by Topics 1–5's mechanisms, applied consistently |
| Identity propagation | Re-authenticate at every hop; pass on-behalf-of context as plain data |

**Where we go next (Topic 7):** key & token infrastructure — the mechanics of JWKS properly (which this note leaned on but didn't fully unpack), key rotation without downtime, and token introspection endpoints for any cases where an opaque (non-JWT) token makes more sense than a self-verifying one.
