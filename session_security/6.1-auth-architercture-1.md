# Topic 6.1 — Microservices Auth Architecture: Pattern A — Auth Embedded in BE

> Scope: Topics 1–5 gave you every individual mechanism (tokens, RBAC, M2M identity). This note zooms out to a single architectural question that sits above all of them: **which deployable in your system is responsible for issuing and being the source of truth for authentication** — and walks through the first of two real answers: keeping that responsibility inside BE, your existing main service. Topic 6.2 covers the alternative (a dedicated Auth service) and closes with a direct comparison and recommendation.

---

## 1. The question this note answers

Every mechanism from Topics 2–5 needs to live *somewhere* in your deployed system:

- Something has to check a password and issue the first access/refresh token pair (Topic 2).
- Something has to hold the JWT **signing** private key (Topic 2 §4.4) — the single most sensitive secret in the whole system, since whoever holds it can mint a valid identity for anyone.
- Something has to own the `roles`/`permissions` tables (Topic 4) and be the place an admin goes to change them.
- Something has to be the identity every other service (Notification, Rewards, and whatever comes later) trusts as "the source of truth for who's logged in."

**Pattern A's answer: that "something" is BE** — no new deployable, no new service. Let's build out exactly what that looks like, then evaluate it honestly.

---

## 2. The shape of Pattern A

```
┌─────────────────────────────────────────────────────────┐
│                          BE Server                          │
│                                                               │
│   /auth/login, /auth/refresh   ← issues tokens (Topic 2)     │
│   holds JWT SIGNING private key (RS256)                     │
│   owns users, roles, permissions tables (Topic 4)            │
│   business logic (listings, orders, ...)                     │
│   calls Notification/Rewards using its own service           │
│      identity (Topic 5)                                       │
└─────────────────────────────────────────────────────────┘
                    │ (publishes JWT verification PUBLIC key)
        ┌───────────┼───────────┐
        ▼                        ▼
  Notification Svc         Rewards Svc
  (verify-only,             (verify-only,
   no signing key)           no signing key)
```

Everything — login, token issuance, RBAC data, business logic — lives in one deployable. Notification and Rewards remain **verify-only**: they hold (or fetch) BE's public key and can check a token's signature and claims, but they never hold anything capable of *issuing* a new one.

## 3. Walking the flows

### 3.1 Login

```
Mobile App ──POST /auth/login {email, pw}──► BE
                                                │ verify password against users table
                                                │ sign access_token with BE's private key (RS256)
                                                │ create + store refresh_token (Topic 2 §5.3)
Mobile App ◄── {access_token, refresh_token} ──┘
```

Nothing new here versus Topic 2 — the point of this note is *where* this code lives, not *how* it works, and here it lives as one more module inside BE, alongside your listings/orders modules.

### 3.2 A downstream service verifying a token

Since BE signs with a private key and everyone else only ever needs the public half (Topic 2 §4.4), Notification/Rewards don't need to call BE on every request to verify a token — they just need BE's public key, fetched once and cached:

```
Notification Svc (on startup, and periodically):
  GET https://be-server/.well-known/jwks.json  ──► BE
  ◄── { "keys": [ { "kid": "2026-06", "kty": "RSA", "n": "...", "e": "AQAB" } ] }

Notification Svc then verifies any token LOCALLY, using the cached public key —
no network call to BE needed per request.
```

This `/.well-known/jwks.json` convention (a **JWKS — JSON Web Key Set** endpoint) is the standard shape for "here are my current public verification keys" and is worth adopting even in Pattern A — it's what makes key *rotation* possible later without redeploying every downstream service (BE can publish a new key alongside the old one, sign new tokens with the new key, and let old tokens naturally expire while verifiers pick up the new key from the same well-known URL).

### 3.3 M2M calls (Topic 5, unchanged)

Pattern A doesn't change anything from Topic 5 — BE still calls Notification/Rewards using its own Cloud Run service identity, still passes `onBehalfOfUserId` as plain context data. The auth-architecture decision in this note is orthogonal to the M2M decision you already made; Pattern A and B both keep Topic 5's design as-is.

## 4. Honest evaluation of Pattern A

### 4.1 What's genuinely good about it

- **Zero new infrastructure.** No new service to deploy, monitor, secure, or keep available. For a solo platform engineer covering GCP infra end to end, this is not a small thing — every additional deployable is one more thing to patch, one more set of logs to watch, one more failure mode in an incident.
- **Fewer network hops for the login flow itself.** Login is already "the user talks to BE" in your system (BE sits behind the load balancer as the entry point) — Pattern A just means the code that handles that request lives where the request already naturally arrives.
- **Simpler mental model for a small team (you).** One codebase to reason about for "how does auth work," rather than context-switching between two deployables to trace a single login flow.
- **Nothing here blocks any of Topics 1–5.** RS256 signing, RBAC tables, refresh rotation, JWKS — every mechanism you've learned works identically whether it's a module inside BE or a separate service. Pattern A vs B is purely about deployment boundary, not about which security mechanisms are available to you.

### 4.2 What it costs you

- **BE's blast radius includes your highest-value secret.** The JWT signing private key now lives inside the same deployable that also runs your general business logic (listings, orders, and whatever you add next). A vulnerability in *any* part of BE's code (an unrelated dependency issue, an injection bug in a completely different endpoint) is now, in principle, one compromise away from the key that can mint tokens for any user. In Pattern B, that key's blast radius is scoped to a much smaller, more auditable codebase.
- **Coupling business logic deploys to auth-critical code.** Every time you ship a change to, say, the listings feature, you're redeploying the same process that holds the signing key and handles login. This doesn't mean deploys are unsafe — but it does mean your highest-security-sensitivity code doesn't get the operational isolation (separate deploy cadence, separate access controls, separate monitoring thresholds) that's often warranted for something this sensitive.
- **Harder to reuse later.** If `mo-marketplace` ever grows a second product surface — a separate seller-dashboard web app, a partner API, a future service — each new consumer of "who is this user" either has to talk to BE for it (coupling a potentially unrelated product to BE's availability) or you end up duplicating auth logic. This is a real, if not urgent, cost given you've told me you expect to stay at 3–5 services.
- **A conceptual asymmetry worth naming:** BE is *both* "the thing that authenticates everyone" *and* "a business logic service with its own concerns" at the same time. That's not incorrect, but it is a slightly awkward role for one deployable to hold — worth being aware of even if you decide it's an acceptable tradeoff for your scale.

## 5. Where Pattern A leaves you

Nothing about Pattern A prevents a clean extraction to Pattern B later, **provided you organize BE's code well now** — a concrete, low-cost thing worth doing regardless of which pattern you pick:

```
be-server/
  src/
    auth/              ← login, refresh, JWT signing, JWKS endpoint, RBAC tables
    listings/
    orders/
    notifications-client/   ← the M2M caller from Topic 5
```

If `auth/` is a genuinely self-contained module (its own routes, its own data access, minimal reach-in from `listings/`/`orders/`), extracting it into its own deployable later is "move this folder, stand up a new Cloud Run service, update everyone's JWKS URL" — not a rewrite. This is worth stating explicitly in your proposal even if you choose Pattern A for now: it's a low-cost decision today that keeps Pattern B available as a future option without having committed to its overhead upfront.

**Topic 6.2 covers Pattern B in the same depth**, then puts both side by side with a direct recommendation sized to your actual 3–5 service scale — plus the remaining general concepts (API Gateway vs. service mesh, Zero Trust for internal traffic, and identity propagation across multi-hop chains) that apply regardless of which pattern you land on.
